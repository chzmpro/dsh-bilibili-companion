→ **`owner_mid = 660490601`**。

## 5. 判断标准（B4/B5/B13/B21）

### 5.1 点赞 / 收藏阈值

```
点赞：score_total ≥ 8  且  score_not_hype ≥ 8      （同一 UP 主一天最多 2 条）
收藏：score_total ≥ 8  且  有复用价值（工具/方法论）
```

### 5.2 推荐给主人（双峰定义，B13 甲）

```
点赞数 ≥ 10000        → 公开 @主号        （大众爆款）
点赞数 ≤ 50 且内容好   → 私信 / 分享给主号 （小众宝藏）
其余（50 ~ 10000）    → 不推荐
```

对应 `config.yaml`：
```yaml
report:
  mention_like_threshold: 10000
  share_like_threshold: 50
```

> ⚠️ 公开 `@` 主号 = **公开暴露小号与主号的关系**（主人已确认保留）。

**`@` 的问题：已解决（纯 API，不需要浏览器）**

原先以为"`@` 必须在评论框里点选候选，所以要么给浏览器、要么放弃"。
**实测发现这个前提不成立** —— B站把"这条评论实际 @ 到了谁"作为
**服务端事实**返回，字段是评论对象的 `content.members[]`：

```json
content: {
  "message": "@MsGsrs @HJQC",        // 正文：只是文本，不算证据
  "members": [                        // ★ 服务端确认的 @ 结果
    {"mid": 282831595, "uname": "MsGsrs"},
    {"mid": 351873378, "uname": "HJQC"}
  ]
}
```

**真机验证**（BV1nFp46qECm 评论区，2026-10-15）：

| 核验场景 | 我们的结果 | 正确？ |
|---|---|---|
| 核验**真被 @ 的人** | `verified`（mid=282831595） | ✅ |
| 核验**没被 @ 的主号** | `failed`，并报出实际 @ 到谁 | ✅ |

**所以做法是**：
1. 发评论时，正文写 `@主号昵称`（B站按**昵称**匹配，写数字 UID 不产生提醒）；
2. 发完**读回**该评论，看 `content.members[]` 里有没有 `owner_mid`；
3. 按结果落四态：

| 状态 | 含义 |
|---|---|
| `verified` | `members` 里确有 `owner_mid` → B站确认提醒已建立 |
| `uncertain` | 读不回 / 评论还没发 / `members` 为空（正文的 @ 只是文字） |
| `failed` | @ 到了**别人**（同名不同 UID）→ 记录实际 UID |
| `unsupported` | 缺 `owner_mid` 或**缺昵称**（数字 UID 无法构造提及） |

**两道独立防线**：`try_mention()` 写库前判定；存储层
`settle_owner_notification(status='verified')` 再断言一次
`observed_mid == owner_mid`，不符直接抛错。

> ✅ **与任务书的冲突已消解**：任务书说"若上游 API 无法可靠表达提及，
> 用隔离浏览器处理该步" —— 现在证明 **API 可以可靠核验**，
> 因此**不需要**给定时 preset 通用浏览器，两边的约束都满足了。

> 📌 本地日报始终可靠生成，不依赖 `@` 是否成功。

### 5.2 推荐给主人（双峰定义，B13 甲）

```

  share_like_threshold: 50
```

> ⚠️ 公开 `@` 主号 = **公开暴露小号与主号的关系**（主人已确认保留）。

**`@` 到底难在哪（大白话）**：
B站发评论时，`@某人` 不是打几个字就行 —— 它要在评论框里**从候选列表里点选**那个人，
B站才会把这条评论真正挂上"提醒他"的关系。如果只是打 `@660490601` 或 `@沐雨林心` 这几个字符，
在 B站看来就是**普通文字**，对方**收不到任何提醒**。

所以程序发完评论后必须**回头看一眼**"页面上那个 @ 到底指向谁"：
* 指向主号 UID → `verified`（真通知了）
* 看不出指向谁 → `uncertain`（不确认成功）
* 指向了**别人** → `failed`（通知错人了）
* 压根没有能力做"点选候选"这一步 → `unsupported`（只留本地日报）

**当前状态**：三步（判定/记录/日报）都已实现并有测试；
但**第四步"点选候选"需要浏览器**，而任务书又明令"定时 preset 不给通用浏览器"——
两者冲突，所以现在落在 `unsupported`：**日报照常给，但不会假称已通知主号**。

> 📌 这条**不影响日常使用**：日报（`docs/` 与 `.local-data/digests/`）本来就是你
> 看汇报的主渠道。`@` 只是"在 B站评论里也提醒一下"的附加动作。

### 5.3 ★ 判断前必须充分了解（B21）

> 搜到可能推荐的视频时，必须**真正了解详尽、充分思考**后再判断，不可只看摘要就下结论。

**在本项目（任务书架构）里怎么落地**：不是"读全文"，而是
**按 `evidence_id` 取短摘录**（≤500 字/次，可多次）核实关键句。
这与任务书"原文不出 bridge"的硬约束一致 —— 见 [`compatibility.md`](compatibility.md) §5。

> ⚠️ **与 curator 的差异**：curator 的 `inspect` 把字幕全文交给 agent；
> 任务书**明令禁止**这种形状（它要求 `read_evidence_excerpt` ≤500 字）。
> 所以此处按**任务书**执行，而不是照搬 curator。

## 8. 验证码（人机检测）—— 执行前必检，**绝不破解**

**实测（2026-10-14）**：B站弹**极验 geetest** 点选，是 `z-index: 2147483647`
**全屏遮罩**；实测点赞按钮命中的是 `DIV.geetest_panel_ghost` → **点击全落遮罩上**。

> ⚠️ ego 插件的 `ego_captcha` **漏报极验**（只认 reCAPTCHA/hCaptcha/Cloudflare/Turnstile）。

```
① 每次【写操作之前】先检测验证码
② 检测到 → 立即停止一切写操作，汇报给主人
③ ★ 绝不尝试自动点选/破解（绕过人机验证 = 红线）
④ 等主人【人工】完成后，再用人用入口恢复
```

**本项目的实现**：`core/health.py` 的 `verification_required` 状态 →
**阻断所有新请求**，且**只能人工恢复**（`cli.app resume`），计时结束也不会自动恢复。

## 12. 与任务书的差异（**重要**）

| 主题 | curator 13 号文档 | 任务书 | 本项目采用 |
|---|---|---|---|
| 原文是否给 agent | `inspect` 给**全文** | **原文不出 bridge**，摘录 ≤500 字 | ✅ **任务书** |
| 谁执行发布 | agent 用**通用浏览器**直接发 | bridge 受控发布 + 门禁 | ✅ **任务书** |
| 定时 preset 工具 | 给 ego 浏览器 | **不给**通用浏览器/shell | ✅ **任务书** |
| 唤醒时机 | — | 建议每日固定时刻 | ✅ **主人定：打开 DSH 时** |
| 人设与频率 | 权威（本文 §2、§5~§10） | 未规定 | ✅ **curator 13 号** |

> 即：**人设与内容规则照 curator 13 号；架构与安全照任务书。**
> 两者冲突时，涉及"是否安全/是否合规"的按任务书，涉及"她怎么说话/怎么判断"的按 13 号。
