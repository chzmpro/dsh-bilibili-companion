## 一、打分机制：问题、根因、修法

### 1.1 你看到的现象

| 视频 | 旧分 | 实际相关性 |
|---|---|---|
| 评论区扎堆的大肥鱼 | **100** | ❌ 讲"B站上一堆 AI 号发一样评论"，跟 DSH 插件无关 |
| 我目前用得最多的一款 DSH 插件 | 97 | ✅ 直接相关 |

**为什么无关的反而更高？** 查出来是**三条叠加**：

### 1.2 根因（三条，全在代码里核实过）

**① 打分标准根本没写**

`core/text_worker.py` 的提示词里只有：

```
"relevance_score":0-100
```

——**只有范围，没有任何定义**。模型只能自己猜"什么算高分"。

**② 系统提示还写着"不做价值判断"**

```
你是内容提取器，只做机械抽取与压缩，不做价值判断
```

于是模型把"打分"理解成"这条内容本身有多充实/多热闹"，
而不是"对主人有没有用"。

**③ 最致命：`analyze()` 连 keywords 都没传给模型**

```python
# 修复前
card = await self.worker.analyze(
    bvid=..., title=..., evidence_blocks=blocks,
)   # ← 没有任何"主人想看什么"的信息
```

⇒ 模型**压根不知道对谁有用**。一条做得热闹的吐槽视频当然拿满分。

### 1.3 修法

| # | 改动 | 效果 |
|---|---|---|
| 1 | **提示词加《打分标准》**：四个维度各 0-100，带分档描述 | 模型知道该按什么打 |
| 2 | **把关注点传给模型**（`focus`） | 模型知道"对谁有用" |
| 3 | **总分由代码按权重算**，不听模型编 | 模型不能靠"讲得有趣"刷分 |
| 4 | **关键词命中下限**（代码算的硬事实） | 明确相关的不被模型保守估分压死 |

**四个维度与权重**：

| 维度 | 含义 | 权重 |
|---|---|---|
| **topic** | 与主人关注点的相关度 | **0.80** |
| usefulness | 能不能拿去用 | 0.10 |
| novelty | 有没有新信息 | 0.06 |
| evidence | 有没有硬依据 | 0.04 |

> ★ 权重**不是拍脑袋**：用 12 条真实视频跑了敏感性分析
> （[`scripts/tune_weights.py`](../scripts/tune_weights.py)），
> topic 占比 → 区分度：`0.60 → +48.8`，`0.80 → +55.5`（最佳），
> `0.50 → +46.1`。所以默认 0.80。

### 1.4 实测效果

同一条视频，**只改打分逻辑、不换内容**：

| 视频 | 旧分 | 新分 | 判定 |
|---|---|---|---|
| 评论区扎堆的大肥鱼 | 100 | **8** | ❌ 正确挡掉 |
| 我目前用得最多的一款 DSH 插件 | 97 | **89** | ✅ 保留 |
| 【插件推荐】榨干 DeepSeek Harness | — | **82** | ✅ 保留 |
| 【我的世界】三分钟学会生成一亿方块 | — | **0** | ❌ 正确挡掉 |
| 让 QQ 机器人开口说话（语音插件） | — | **0** | ❌ 正确挡掉（跟 DSH 无关） |

**12 条样本的区分度**：相关组均值 70.7 / 无关组 15.2 ⇒ **+55.5**。

### 1.5 ★ 设置页可以调

新增 `discovery.score_topic_weight`（0.5~0.95，默认 0.80），
在设置页「挑什么、挑多少」分组里。

| 值 | 效果 |
|---|---|
| 调高（0.9） | 更严格"只看跟我有关的"，可能漏掉沾边的好内容 |
| 调低（0.6） | 更看重内容质量本身，容易放进"热闹但无关"的 |

> ★ **只开放一个旋钮**（topic 占比）是刻意的：四个维度各自可调
> 在十几条样本上**必然过拟合** —— 随便调都能凑出好看的区分度，
> 换个样本就崩。一个参数既够表达"严不严"，又能被真实数据验证。

### 1.6 怎么自己验证

```bash
# 用真实库里的视频重新打分，看区分度
./.venv/Scripts/python.exe -u scripts/eval_scoring.py --limit 10 --evidence 30

# 采样 + 扫权重（纯计算，秒出）
./.venv/Scripts/python.exe -u scripts/tune_weights.py --sample --limit 12
./.venv/Scripts/python.exe -u scripts/tune_weights.py
```

## 二、私信实时回复

### 2.1 结论：**可行，而且比评论更简单**

主人判断得对：

> 「你也不确定别人什么时候评论你，你再回复，我私信你应该效果一样」

评论要轮询**全站评论串**，而私信只要查**一个数字**：
`follow_unread`（未读数）。这就是 B 站消息弹窗背后的那个数字。

### 2.2 三条约束

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **只查未读数**，数字变了才拉正文 | 省请求；不读无关数据 |
| 2 | **只回主人** | 接收者硬编码 `owner_mid`，代码层无法发给别人 |
| 3 | **幂等**（按 `msg_seqno` 去重） | 回复后未读数**不会立刻归零**（要等对端读），不去重就会**同一句话回 N 遍** |

### 2.3 用法

```bash
# 只看有新消息没有（不发送）
./.venv/Scripts/python.exe -m cli.app dm-poll

# 发现新消息就回复（只回最新一条）
./.venv/Scripts/python.exe -m cli.app dm-poll --reply --text "好呀～" --yes
```

**实测**（真机，2026-10-17）：

```
未读数（主人发来的）：1
发现 6 条未回复的消息：
  [10-14 13:56] 我们已互相关注，开始聊天吧~
  [10-16 13:22] 学习一下然后给我介绍是否适合你装
  [10-16 13:22] 【完全开源】实测比 HyperFrames 更快的 AI Agent 视频渲染器
                （分享卡片：BV1g8Jy6FEpD）
  [10-17 10:05] 找点好用的插件呗，例如免费搜索插件这样的
```

回复后**再跑一次** → `未读数：0`，**没有重复发送**（幂等生效）。

### 2.4 门禁

私信走 `interaction.dm_reply_enabled` **独立开关** ——
与公开发布的 `mode`/`dry_run`/`publish_enabled` **无关**
（回复主人私信不是公开动作）。

但仍然是**写入**，所以：写请求**不重试**、阻塞态（验证码/风控）**不发**、
正文 ≤ 500 字符。

### 2.5 ⚠️ 关于"持续监测"

现在 `dm-poll` 是**手动跑一次**。要做成"随时回复"，需要让它**周期性跑**。

两种接法（**都还没做，等你定**）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 接到持续跑循环** | 每轮 `run_once` 顺手 `dm-poll` 一次 | 改动小，但响应受轮次间隔限制（30 分钟） |
| **B. 独立高频轮询** | 单独每 N 分钟查一次未读 | 响应快，但请求次数更多 |

> ⚠️ 我**不建议**把间隔调到几分钟以内 —— 那会明显增加请求频率，
> 与本项目"不加大请求强度"的红线冲突。折中：**5~10 分钟**查一次未读数
> （一个数字的 GET，成本极低），发现新消息再拉正文。
