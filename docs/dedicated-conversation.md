# 小鲸鱼专用对话：入口与自动唤醒（回答主人三问）

> 主人说：「我准备用一个完全的对话作为小鲸鱼的专属对话，这意味着你需要让另一个对话
> 看到项目且 DSH 是开启状态就需要进行任务」+ 两个关于记忆的问题。
> 本文把这三件事说清楚，并给出**可执行的落地方案**。

---

## 一、让新对话"看到项目" —— 入口文件

DSH 的 agent 每次开工都会读工作区里的 `AGENTS.md`。所以只要在
**项目目录**放一份 `AGENTS.md`，任何在项目里开的会话都会自动读到它。

已创建：`projects/dsh-bilibili-companion/AGENTS.md`

它的作用是让新对话**第一件事就做对**：

1. 先读 `START-HERE.md`（30 秒看懂）
2. 调 `companion_status` 看今天该不该干活
3. 按 `docs/persona.md` 的人设与规则行动
4. **绝不**绕过 bridge 直接发东西

> ⚠️ 但要注意：**DSH 只读工作区根或会话 cwd 的 `AGENTS.md`**。
> 所以有两种接法，见 §二。

---

## 二、让"DSH 一开就干活" —— 两种接法

### 接法 A（推荐）：专用会话 + 开场指令

DSH 的 Schedule **不保证恰好投递一次**，也不适合"每次开 DSH 都跑"。
而本项目已经实现了 `schedule.mode: on_host_start` ——
**判定逻辑在 bridge 里**，所以更简单可靠的做法是：

```
① 固定一个对话当"小鲸鱼专用对话"，cwd 设为项目目录
   （这样它会自动读到项目的 AGENTS.md）
② 该对话的第一句话固定为：

     开工。先调 mcp__bili_companion__companion_status 看 schedule.due；
     是 true 就 prepare_batch 跑一轮，然后按 docs/persona.md 汇报。

③ DSH 一开，你切到那个对话，发这句话（或直接继续上次对话）
```

**为什么这样最稳**：
- `companion_status.schedule.due` 已经带了**防抖**（默认 120 分钟内不重复跑）
  和"今天跑完没有"的判断 → **反复开关 DSH 也不会重复干活**
- 不依赖 DSH 的日程投递语义
- 你能随时看见它做了什么

### 接法 B：DSH 原生日程

如果你想要"完全不用管"，可以在 DSH 里设一个日程，唤醒 `bili-companion` preset。
但按官方语义：

| 官方语义 | 影响 |
|---|---|
| 宿主运行期间才调度 | DSH 关着就不会跑 |
| 投递记录不代表模型完成 | **不能**用"提醒发出去了"当"任务做完了" |
| 不保证恰好投递一次 | 可能重复/遗漏 → 必须靠本项目的幂等键兜底 |

→ 本项目**已经**为"重复投递"做好了防护（幂等键 + `uncertain` 冻结 +
`min_gap_minutes` 防抖），所以两种接法都安全。

> 详见 [`schedule-wiring.md`](schedule-wiring.md)。

## 三、★ 问题 1：上下文多了会不会"忘记"？

**会。** 这是 LLM 的固有特性，本项目无法改变 DSH 的压缩行为。但——
**本项目的设计恰好让"忘不忘"不影响正确性**，因为**状态不在对话里**。

| 类型 | 例子 | 会不会丢 | 后果 |
|---|---|---|---|
| **对话里的口述约定** | 「以后少点赞」「那个 UP 主不喜欢」 | ⚠️ **会丢** | 可能行为漂移 |
| **数据库里的硬状态** | 赞过谁、藏过谁、今天用了多少配额 | ✅ **不会丢** | 已赞的再赞会被 `ALREADY_LIKED` 拒 |

### 已经用代码兜住的部分（不依赖对话记忆）

| 关注点 | 靠什么保证 | 丢失对话记忆会怎样 |
|---|---|---|
| 不重复点赞/收藏 | 幂等键 + `video_states` | 再点会被拒绝，**不会重复** |
| 不重复评论 | 幂等键（`agent_mid+bvid+top`） | 再发会被 `DUPLICATE_ACTION` 拒 |
| 不超额 | `actions` 表按天统计配额 | 超额被拒 |
| 不确定动作不重发 | `uncertain` 冻结 | 即使"忘了"，也不会重发 |
| 收藏夹归对类 | `favorite_folders` 缓存名→id | 不依赖对话记忆 |

### 会受影响的（**建议写进配置，别只靠对话说**）

| 事项 | 建议 |
|---|---|
| 兴趣关键词 | 写进 `config.yaml` 的 `discovery.keywords`，不要只在对话里说 |
| 频率偏好 | 写进 `interaction.frequency_tier` |
| 谁不能互动 / 特别偏好 | 目前没有对应配置项 → **可以加**（见 §五） |
| "主人说过的话" | 需要一份**跨对话的持久笔记**（见 §五） |

> **一句话**：**能写进配置/数据库的，就不要只写在对话里。**
> 对话是"工作台"，数据库是"档案柜"。

## 四、★ 问题 2：换对话后，之前的互动记录还在吗？

**在。** 已实测（新开一个进程、只调 MCP 工具）：

```
数据库（与对话完全无关）：
  D:\DeepSeek\projects\dsh-bilibili-companion\.local-data\companion.db

已落库的真实历史：
  10-15 16:03  like      sent_verified  sim=0
  10-15 16:03  favorite  sent_verified  sim=0
  点赞/收藏状态: like_state=1 fav_state=1 fav_media_ids=[4265226629]
  收藏夹缓存  : [('工具与技术', 4265226629)]
  看过的视频  : 35 条
  证据片段    : 257 条
```

**新对话能看到的历史**（都通过 MCP 工具读，不需要旧对话）：

| 工具 | 能看到 |
|---|---|
| `companion_status` | 最近运行、今日配额、待审草稿、`@` 投递统计、token 用量、调度状态 |
| `list_drafts` | 所有草稿（含已发/待审/不确定） |
| `check_interactions` | 已见回复去重状态 |
| `read_evidence_excerpt` | 任何历史证据的短摘录（按 `evidence_id`） |
| `feedback` | 主人给过的评价 |

**实测：新对话再点同一个赞** → 幂等键命中 → 返回 `ALREADY_LIKED`，
**不会重复点**。也就是说：**即使新对话"不记得"，也不会做错事**。

## 五、还有两个缺口（诚实标注，需要时我来补）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1 | **没有"跨对话的持久笔记"** | 主人在对话里说过的偏好（"少点赞""这个 UP 别碰"）会随对话丢失 | 可加一张 `owner_preferences` 表 + 一个工具读写；或把偏好写进 `config.yaml` |
| 2 | **没有"对话开场自动提示"机制** | 新对话不会自动知道"该开工了" | 靠 `AGENTS.md` + 固定开场句（§二接法 A）；或接 DSH 日程（接法 B） |

> 这两条**不影响安全**（不会误发），只影响"顺不顺"。要不要做请主人定。

## 六、给"小鲸鱼专用对话"的固定开场句（可直接复制）

```
开工。按 projects/dsh-bilibili-companion/AGENTS.md 执行：

1. 调 mcp__bili_companion__companion_status
2. 看 data.schedule.due：
   - true  → 调 prepare_batch 跑一轮，然后按 docs/persona.md 汇报
   - false → 告诉我"今天已完成或防抖跳过"，不要重复干活
3. 汇报用 docs/persona.md §9 的模板
4. 默认 observe + dry_run：不要尝试任何真实发布
```
